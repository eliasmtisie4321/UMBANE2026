## 5. Release blockers and risks found in project documentation

### P0 — Verify production migration 0018

Latest main commit introduces `20261202000018_search_calendar.sql`, required for global search, calendar events/feed and personal Google Calendar connection support. The production launch checklist states all migrations must be applied in filename order. Run `npm run verify:prod` against production and confirm migration 0018 is listed as applied before releasing calendar/search functionality.

The prior documented production verification (27 Nov 2026, earlier run) reported 44 passed, 1 warning, 0 failed, with the warning being open sign-up. That result predates the latest main commit and does not establish migration 0018 is live.

### P1 — Authentication configuration

The launch guide says production should turn off public “Allow new users to sign up”, keep email confirmation enabled, set Site URL and redirect URLs for `/reset-password` and `/welcome`, and configure custom SMTP for password-reset mail. The previous production check warned that open sign-up was enabled. Confirm the warning has been resolved.

### P1 — Integration readiness

The integration docs explicitly say real provider accounts/approvals are still needed to exercise Google/Microsoft OAuth, Gmail scope verification, Meta permissions and business verification, WhatsApp approved templates, LinkedIn app permissions and a Twilio sender capable of South African delivery. The adapters' automated tests use recorded provider responses; they are not live provider acceptance tests.

Required server configuration includes `INTEGRATIONS_KEY` and `APP_URL`, plus provider-specific OAuth/API settings. Confirm presence and correct configuration in Vercel without exposing values in logs or this report.

### P1 — Real signed-in acceptance testing

The launch checklist remains unchecked for:
- Administrator, manager, staff and client sign-in and role-specific menu/access behaviour.
- Creating a customer, property and meter, then recording a meter reading.
- Creating/issuing/sharing an invoice by email, checking its PDF, recording a payment and confirming balances.
- Receiving stock, fulfilling an order and confirming stock movement.
- A client opening a ticket with an attachment and staff replying/resolving it.
- Sending an employee invitation and completing the Welcome/password flow.
- CSV/PDF report export and email sharing.
- Communications delivery status.
- Phone sign-in, ticket submission and invoice viewing.

### P1 — Accessibility and cross-browser manual verification

The QA guide's manual release checks are unchecked for full keyboard operation, focus restoration, screen-reader announcements, latest supported Chrome/Edge/Firefox/Safari, real iPhone Safari/Android Chrome, and tablet portrait/landscape. Automated axe checks and a single focus-ring test do not replace these.

### P2 — Backup and recovery

The launch guide requires confirming a database backup from the last 24 hours and a restore into a separate project. It also notes Supabase database backups do not include Storage files or secrets. Confirm backup, attachment export and secure secret recovery plans.

### P2 — Planned/deferred product scope

Implementation plan notes also call out unfinished or conditional items: dashboard growth/registration/outstanding payment/maintenance panels; customer document upload; meter photo upload/live telemetry/tariff-based rand estimates; real provider sandbox testing; Google Calendar API + `calendar.events` scope and Google verification; and first real customer/business records. These should be treated as scope/launch dependencies where the client expects them.

## 6. Security and architecture observations

The QA and architecture documentation describes:
- Supabase Row Level Security as the authoritative role/data boundary.
- Server-only service-role and provider secrets.
- Private Storage buckets with signed links.
- Server-side validation and rate limiting.
- Security headers configured in `vercel.json`.
- Audit logging and redaction controls.

Database tests pass in CI, including RLS/migration checks. Still complete the real development/production Supabase verification described by `docs/PERMISSIONS.md`; an in-memory PGlite stand-in is not the actual Supabase runtime.

## 7. Recommended release execution order

1. Apply migration 0018 to the intended production Supabase project (only if not already applied); run `npm run verify:prod` on the latest deployment.
2. Turn off open sign-up, verify email confirmation, Site URL, redirect URLs and SMTP.
3. Confirm Vercel production environment variable names are configured; check integrations key/app URL and each provider required by the client.
4. Run signed-in role smoke tests with separate administrator, manager, staff and client accounts.
5. Execute the core customer → property → meter → reading; invoice → email/PDF → payment; stock → order fulfilment; ticket → attachment → staff response workflows.
6. Test invitations, exports, communication delivery, mobile layouts and provider sandboxes/live test accounts.
7. Complete keyboard/screen-reader/browser/device checks and backup restore drill.
8. Record evidence, defects and final acceptance from the client before declaring production sign-off.
